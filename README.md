existing WordPress site as a maintainable, database-backed application with

## Overview

The project rebuilds `thealphahealthgroup.org` as a Django + PostgreSQL
application. The goal is not to reproduce the WordPress site page-for-page,
but to build a proper CMS for the organization that:

- separates presentation from content;
- stores all business content in PostgreSQL;
- lets authorized staff manage content through Django Admin, with no
  developer required for routine updates;
- supports rich, multi-image project pages;
- supports a CSSD/medical product catalogue;
- captures contact and product enquiries;
- produces clean, stable, environment-independent URLs;
- models the organization's two operating entities (US and Ghana) without
  duplicating content or code.

### Known issues in the current site this rebuild fixes

- Images reference `http://localhost/...` directly in content, so they're
  broken for every visitor. All internal links and media references will be
  generated by Django, never hard-coded.
- Testimonials are placeholder copy (`"Your glowing words will go here
  soon..."`) attributed to invented names. These will not be migrated as
  real content — the site launches with zero testimonials rather than fake
  ones.
- The footer copyright link points to a non-existent page.

## Tech Stack

| Layer | Choice |
|---|---|
| Language | Python |
| Framework | Django |
| Database | PostgreSQL |
| Rich text editor | django-ckeditor-5 (in-admin WYSIWYG) |
| HTML sanitization | `bleach`, applied on save |
| Media storage (MVP) | Local disk via Django `FileSystemStorage`, abstracted behind `STORAGES` setting |
| Thumbnails | `django-imagekit` (or equivalent `Pillow`-based resize on save) |
| Frontend | Django Templates, HTML, CSS, JavaScript (no SPA framework) |
| Dev environment | Git, GitHub, Python venv, PostgreSQL, optionally Docker Compose |

No React/Next.js frontend, no e-commerce checkout, no CRM, and no custom
permissions system in the first version — see [Roadmap](#roadmap) for what's
deliberately deferred.

## URL Structure

Public routes:

```text
/
/about/
/services/
/services/<slug>/
/projects/
/projects/<slug>/
/team/
/products/
/products/<slug>/
/products/category/<slug>/
/contact/
```

Administrative:

```text
/admin/
```

**Principles**

- Human-readable, slug-based, generated by Django's named URL patterns —
  never manually constructed or environment-specific.
- No `?p=362`-style query IDs.
- No `localhost` or hard-coded production domain ever stored in database
  content — this is the direct fix for the current site's broken-image bug.

### Slug Strategy

Slugs are generated from titles on creation. Once a Project is **published**,
changing its slug is treated as a deliberate action, not a side effect of
editing the title — an unpublished Project's slug may regenerate freely. The
`Redirect` model exists specifically to preserve old URLs when a published
slug does change.

## Media & Rich Text

**Rich text.** `django-ckeditor-5` provides in-admin WYSIWYG editing for
`Project.content`, `Service.description`, `TeamMember.biography`, and
`Organization.description`. Content is run through `bleach` with an explicit
allowlist (`p, h2-h4, ul, ol, li, a, strong, em, blockquote, img, table, tr,
td`, etc.) on save — not only at render time — stripping `<script>` tags,
inline event handlers, and `javascript:` hrefs. Short fields (`excerpt`,
`short_description`) remain plain `TextField`.

**Media storage.** Local disk for MVP, via Django's `FileSystemStorage`,
but referenced only through the `STORAGES` setting rather than directly in
code, so a later move to S3-compatible storage or a CDN is a configuration
change, not a code change. Uploaded images are organized by model
(`media/projects/<id>/`, `media/products/<id>/`, etc.), and thumbnails are
generated at upload time (`django-imagekit`) so listing/card views never
serve full-size originals.

## Getting Started

```bash
# clone and enter the repo
git clone <repo-url>
cd alpha_health

# create and activate a virtual environment
python -m venv .venv
source .venv/bin/activate

# install dependencies
pip install -r requirements.txt

# copy environment template and fill in local values
cp .env.example .env

# set up the database
createdb alpha_health_dev
python manage.py migrate

# create an admin user
python manage.py createsuperuser

# run the development server
python manage.py runserver
```

Visit `http://localhost:8000/` for the public site and
`http://localhost:8000/admin/` for content management.

## Environment Variables

Configuration is environment-based; `.env` is never committed, `.env.example`
always is.

```text
DJANGO_SECRET_KEY=
DJANGO_DEBUG=
DATABASE_URL=
ALLOWED_HOSTS=
EMAIL_HOST=
EMAIL_PORT=
EMAIL_USERNAME=
EMAIL_PASSWORD=
```

- **Development**: console email backend, `DEBUG=True`, `localhost` allowed
  host.
- **Staging**: staging domain, real SMTP, `DEBUG=False`.
- **Production**: `thealphahealthgroup.org`, transactional email provider,
  `DEBUG=False`, HTTPS enforced, secure cookies.

The application must behave identically across environments without any
change to database content.

## Deployment

```text
                    Internet
                       │
                       ▼
                Reverse Proxy
                       │
                       ▼
                Django / Gunicorn
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
         PostgreSQL          Media
```

- Static files served directly by the reverse proxy in production, not
  through Django.
- HTTPS enforced; secrets never committed to Git.
- **Backups**: daily PostgreSQL backup plus periodic restore verification;
  media backed up separately. A backup isn't considered reliable until a
  restore has actually been tested.
- **Error pages**: `404.html`, `403.html`, `500.html` — technical details
  stay in server logs, never shown to visitors.

## Roadmap

### MVP (this build)

Public: Home, About, Services (+detail), Projects (+detail), Team,
Products (+detail, +category filter), Contact.

Admin: full content management for all of the above, plus contact
enquiries, via Django Admin.

Infrastructure: PostgreSQL, Django, auth, media handling, static files,
environment config, tests, logging, deployment config, Redirect model.

### Explicitly out of scope for MVP

E-commerce/checkout, online payments, inventory management, hospital
inventory integration, patient management, medical records, a CRM, a
custom React frontend, a separate blogging platform, a complex custom
permissions system (Django Groups/Permissions are sufficient initially),
a mobile application, search.

### Phase 2

Custom admin dashboard, project categories, search (Projects/Services/
Products via PostgreSQL full-text search), advanced filtering, SEO
metadata fields, analytics, newsletter integration, automated email
workflows, content scheduling, audit logs.

### Phase 3

Partner/client portal, project impact metrics, downloadable reports,
research publication management, events, grant/program management,
advanced analytics, public API, external integrations.

## Engineering Principles

1. Don't duplicate data — if it's in the database, don't hand-copy it into a template.
2. Don't hard-code relationships — use foreign keys and named Django routes.
3. Don't over-engineer — build what's needed now, not what might be needed.
4. Prefer Django's built-ins over custom auth, permissions, or admin.
5. Make content editable — routine changes shouldn't require a developer.
6. Keep presentation separate from data — templates render, models store.
7. Design for change — simple now, extensible later.
8. Test the workflows that matter most: publishing, enquiries, admin actions.
9. Treat production as a genuinely different environment — never depend on
   localhost-specific configuration.
10. Build incrementally — every phase should leave something working.

```text

Phase 2  Core website      Header, nav, footer, global CSS, Home, About
Phase 3  Projects          Project + ProjectImage models, admin, listing, detail, publishing logic, tests
Phase 4  Services          Model, admin, listing, detail, tests

Phase 6  Products            ProductCategory + Product, admin, catalogue, detail, filtering, enquiry flow

Phase 9  Deployment              Production PostgreSQL, Gunicorn, reverse proxy, static/media, HTTPS, backups, monitoring
```

**Immediate next step:** the `core` app (Organization + Redirect models),
followed by the `projects` app — Projects are the most content-rich entity
and establish the patterns (rich text, multi-image, org-scoping) that every
other app reuses.
